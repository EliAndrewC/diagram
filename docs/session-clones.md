# Session clones and the stop-work procedure: the full spec

*Project reference, split out of [`../CLAUDE.md`](../CLAUDE.md) so it is loaded on demand rather than in every session's context. CLAUDE.md keeps the short always-on version of these rules and points here for the full spec.*

**Load this file when:** setting up a clone for a session, hitting a clone/sync hook block, resolving a push conflict, or anything about render-sync. CLAUDE.md carries the short version that covers the normal path.

**Session clones (REQUIRED for every session that modifies this repo)**: any session that is about to change a file in this repo first makes an **isolated clone under `.clones/`** and does all of its work there - this is the standard workflow for every code-modifying session, not just for known-parallel work. A shared working tree is what causes the cross-session pain: constant "file modified since read" churn on shared files (`settlement.py`, `pyproject.toml`, ...), a `git status` that mixes multiple features' uncommitted work, and test-globs (`test_villages` globbing `pool/*/*.gen.py`, etc.) picking up another session's in-flight files. The clone is the workspace; main `/diagram` is the integration point. Sessions that only *read* this repo, or that only write to `/host-l7r-repo`, Obsidian Portal, or the scratchpad, do not need a clone.

- **Clone name = the Claude Code session name, kebab-cased**: lowercase, spaces to hyphens, punctuation dropped. "Diagram (city)" -> `.clones/diagram-city`; "miscellaneous" -> `.clones/miscellaneous`. **Resolve YOUR OWN session name reliably - do NOT guess or default** (GM 2026-07-22, after a session that ignored its name defaulted to the shared clone and collided with another that did the same): your `session_id` is in your scratchpad path; the LAST `{"type":"custom-title","customTitle":...}` line in `~/.claude/projects/<cwd-mangled>/<session_id>.jsonl` is the name (`/rename` writes it synchronously; `/clear` mints a new `session_id` and re-emits it as line 1 of the new transcript; `--resume` carries it). Only if there is none, grep `~/.claude/sessions/*.json` for that id and read its `.name` - that file is the process's STATUS record, rewritten asynchronously, and reading it first is what made names look "lost" after `/clear` (GM 2026-08-27; `clone-sync-hooks.sh canonical_clone` now reads the transcript first, via the hook input's `transcript_path`). The sessions-json filename is the session's PID and its body carries `{"id": "<your session_id>", "name": "...", "nameSource": ...}`, so the id is the reliable key (the `<pid>.json` framing assumed you know your PID - you usually do not). `nameSource: "derived"` means an auto-generated title, not a GM-chosen name; a GM-set name must never be overridden.
- **`diagram` - this repository's own name - and `gm-assistant` are FORBIDDEN clone names** (GM 2026-07-22; the hook forbids the basename of whichever main it runs under): it is the repository, not a session, and being the old unnamed-default is exactly what let two sessions share one working tree. There is no "default clone" anymore. A session that is unnamed, has an auto-derived title, or is literally named "gm assistant" therefore has no valid workspace: **stop and ask the GM to `/rename` it to something distinct before doing any repo work** (Claude cannot rename a session from inside it - `/rename` is user-facing only, verified 2026-07-20). The tooling enforces this - `scripts/sync-with-main.sh` refuses to run from `.clones/gm-assistant`, and the PreToolUse hook blocks edits that resolve or route to it - so if you hit that error, relay it and have the GM rename the session.

  **ASK IN TURN 1, NOT AFTER THE RECON** (GM 2026-08-08). The `prompt` hook now checks the name on the FIRST prompt of any session that has not claimed a clone yet, and says so once if it does not resolve. The pretool backstop is a backstop: it only fires at the first EDIT, by which time the session has done all its reading and planning and the rename is pure dead time - measured at 4.6 minutes on 2026-08-08, after 4.7 minutes of recon that could have run concurrently with it. If you are going to modify the repo, get the name settled while you still have other work to do. (A read-only session needs no clone and is not nagged - the notice fires once and never blocks.)
- **Clone isolation is ENFORCED by the PreToolUse hook** ([`scripts/clone-sync-hooks.sh`](../scripts/clone-sync-hooks.sh), tested by [`scripts/test-clone-sync-hooks.sh`](../scripts/test-clone-sync-hooks.sh)): at a clean work-unit boundary it (1) blocks the forbidden `gm-assistant` clone / unnamed sessions, (2) NAME-ROUTES - blocks any edit whose clone is not `.clones/<this session's resolved name>`, so a session cannot wander into another's clone or the shared default, (3) CLAIM-BACKSTOP - blocks a clone another **live** session already occupies (deterministic liveness: session_id -> PID = the sessions-json filename -> `/proc`, so a previous same-named session's stale claim never blocks a legitimate reuse), (4) blocks a clone whose HEAD is behind main. A DIRTY tree is always allowed (mid-task work is sacred; guards run only at clean boundaries). Because every session runs main's copy of the hook via the absolute path in `.claude/settings.json`, changes to it take effect for all sessions at once - keep `test-clone-sync-hooks.sh` green.
- **`.clones/` is gitignored and lives on the host mount** (`/diagram` is bind-mounted), so clones survive container rebuilds. If `.clones/<session-name>` already exists (a resumed session), reuse it - do not re-clone.
- **Sync in at the start of EVERY new piece of work, not just at the final push - now ENFORCED by harness hooks** (GM 2026-07-21, wired in `.claude/settings.json` + [`scripts/clone-sync-hooks.sh`](../scripts/clone-sync-hooks.sh)): a UserPromptSubmit hook auto-runs `sync-with-main.sh sync-in` (git pull) on the session's known clone at every GM message while its tree is clean, and a PreToolUse hook BLOCKS Edit/Write in any clone whose tree is clean but whose HEAD is behind main - a work-unit boundary on a stale base. A dirty tree is never touched or blocked (mid-task work is sacred). Renders are NOT synced into the clone (GM 2026-07-22): `render-sync` regenerates main's renders in place from main's own tip, so nothing flows clone -> main and a clone never needs main's renders - it regenerates whatever map it iterates on. Whenever a GM message kicks off new work in an existing clone - a resumed session, or the next task in a long-lived session - run `git pull origin main` inside the clone before touching anything. Other sessions push improvements to main between your tasks (test speedups, shared-file fixes), and new work must not build on a stale base. The pull is near-free at this moment (the clone has nothing uncommitted, so it's almost always a fast-forward), and any conflict surfaces at the cheapest possible time - before new work exists - instead of at the stop-work push-back. A fresh `git clone` is born synced, so this only applies from the second work unit onward.
- **Create the clone (cheap):** `git clone <main> .clones/<session-name>` (main is `/diagram` for this repository, `/gm-assistant` for gm-assistant - the hooks derive it from the git root, never a literal) - a local clone hardlinks the object store, so it is near-instant and does not double the disk. Since feature 130 the clone's `origin` is GitHub (`https://github.com/EliAndrewC/diagram`, HTTPS + the PAT via `scripts/git-askpass-token.sh`) - the procedure re-points a freshly cloned `origin` itself on its first run - so `pull origin main` / `push origin HEAD:main` talk to the integration point directly and `/diagram` is only a mirror. Repo-local git config does NOT copy over, and since 2026-08-25 nothing needs setting by hand: `sync-with-main.sh` (every mode, including the prompt hook's automatic `sync-in`) sets the clone's `user.name`/`user.email` from the author of main's tip commit when they are missing, and says so. If you must commit before any procedure has run in a brand-new clone, `git config user.email` is empty - run `scripts/sync-with-main.sh sync-in` first rather than typing the identity.
- **Git ownership.** Inside the clone, and for syncing the clone back into main, the session performs ALL git actions itself (add / commit / merge / push-back to main). Since feature 130 the session's push goes to GitHub main itself (directly, or through the merge build), so the GM has no laptop-side push job for this repository any more - a push they make to GitHub main flows into the mirror and every clone like any other landing. Never commit or push against `/host-l7r-repo` (per the Core Rules).
- **A clone captures only committed state.** Under this workflow main is normally fully committed, but the GM's own in-progress edits in main may not be - if the task depends on the GM's latest hand edits, ask them to commit first; otherwise note that uncommitted main-tree files are absent from the clone.
- **Stop-work procedure - run EVERY time you stop working** (reporting a task done, reaching a milestone, or pausing for GM input). **SCRIPTED (GM 2026-07-21): run [`scripts/sync-with-main.sh`](../scripts/sync-with-main.sh) from inside the clone instead of hand-typing the steps** - `sync-with-main.sh sync-in` (start of work), `sync-with-main.sh push` (commit first yourself; locked pull+push, exit 3 = incoming changes overlapped your files, rerun the gate and fix forward), `sync-with-main.sh render-sync` (regenerates main's renders IN PLACE from main's tip, cache-short-circuited, under the lock), `sync-with-main.sh done` (push + render-sync). Hand-typed procedures caused every sync incident on record (skipped flock, wrong-cwd rsync, error-suppressed cp, stray Mode A outputs); the numbered steps below are the SPEC the script implements - and the fallback if it misbehaves:
  1. **Commit** all work in the clone with a normal descriptive message.
  2. **The push, by ONE of TWO ROUTES chosen from your delta - never by you** (feature 130, 2026-08-25). `sync-with-main.sh push` fetches GitHub `main` (the integration point since feature 130; `/diagram` is a MIRROR of it), inspects what YOUR commits changed since the merge base (what you merged in from main never counts), and:
     - **DIRECT** - no diagram engine code in the delta (docs, specs, config, `.notes.md`, the append-only logs): today's locked pull + fast-forward push to GitHub main, free:

       ```
       flock <main>/.clones/.sync.lock sh -c 'git pull --no-rebase origin main && git push origin HEAD:main'
       ```

     - **GATED** - engine code (`l7r/**/*.py`, `tests/`, `pool/*.gen.py|*.json` - the code the tests exercise; the Makefile, `pyproject.toml`, the lockfiles and `scripts/` shape how the gate runs, are covered locally, and never dispatch): `make ci-merge`. Five conditions are checked locally first (`make ci-status` shows them, free): the delta, a NAMED and COMPLETE spec-kit feature (no open task, spec FAITHFUL), a GREEN local check (`quick`/`reference`/`test-file`/a local `done`) against exactly this code, no verified record for the tree already, the breaker up. Then lint locally, a CodeBuild build started and parked, `make _reference` locally, and on green the build merges the LATEST GitHub main into the work, runs `make done`, and fast-forward-pushes the result to GitHub main itself; the clone and the mirror fast-forward to what landed. A tree a green `make ci-check` already verified merges with no build (SKIP-VERIFIED). **There is no local override of the gated route** - a delta that cannot be dispatched stays in the clone. `done FULL=1` runs the full sweep on CodeBuild after the local prompt (the GM's to answer).

     The flock serializes every session's pull-and-push (two sessions finishing in the same minute is real - it happened 2026-07-20, two pushes landing in the same second), so no other session can slip a push into the gap between your merge of main's tip and your push. The lock is held only for the seconds the pull+push take. Main has `receive.denyCurrentBranch = updateInstead` set, so the push also updates main's working tree - `sync-with-main.sh` sets it if a fresh checkout lacks it (and `setup-dev-env.sh` does on a fresh container), so there is no longer a one-time step to remember.
  3. **If the locked command fails, fix in the clone and re-run it - NEVER `git push --force`.** The failure modes:
     - **Merge conflicts** (the pull stopped): resolve them in the clone, and if the merge brought in someone else's changes to files you touched, rerun the relevant gate (`make done` for webapp work, the skill's `pytest --cov` for skill work) - conflict resolution and gate runs happen OUTSIDE the lock (a 15-minute test run must never hold it) - then commit the merge and re-run the locked command. This converges: each round merges whatever landed meanwhile.
     - **Clean auto-merge that touched your files** (the locked command succeeded, but the pull's merge combined someone else's edits with yours in the same files): the push has already happened, so rerun the relevant gate NOW and **fix forward** - commit any fix and run the locked command again immediately. A briefly-broken main between the two pushes is tolerable because every session's sync-in gate rerun catches it; an unexamined semantic clash is not. **And note what `exit 3` costs: `done` is push-THEN-render-sync, so this branch stops before render-sync and main keeps its OLD renders.** That is deliberate - regenerating main's pictures from a tip whose gate has not been re-run would be the wrong cure - but it is silent unless you act on it, and on 2026-08-12 two syncs in a row hit this branch and the GM was shown a map whose connector had been re-routed clear across the sheet while the PNG still had the old route. So once the gate is green again: `scripts/sync-with-main.sh render-sync`. The script says so in the failure message too.
     - **Push rejected as non-fast-forward** (only possible if the lock was skipped): the rejection is git's ref serialization working as designed - the answer is another pull/retest/push round, never force. Forcing is the ONE thing that overwrites other sessions' work (2026-07-20: a session answered this rejection with a force push and briefly clobbered main's branch; recovered via the reflog).
  4. **The mirror follows, fast-forward only.** After either route the procedure runs `git -C /diagram pull --ff-only origin main` under the lock. If that is refused, someone committed in `/diagram` by hand - the procedure stops and says so ("mirror cannot fast-forward"); move that work into a clone. Nothing pushes INTO `/diagram` any more; `updateInstead` stays configured and is harmless.
  5. **Regenerate main's diagram renders in place (GM 2026-07-22, replacing the old build-in-clone-then-copy machinery).** Main's working tree is where the GM browses EVERY pool render in one place, so the gitignored derived renders (Mode B `.svg`+`.png` in `pool/{hamlets,villages,towns,provincial-cities}/`, Mode A `.png` in `pool/magistracies/`) must be current in main even though git never carries them - stale or missing renders in main are a bug, not "normal drift". The old approach BUILT renders in the clone and COPIED them into main (rsync + tip-guard + byte-verify); that was fragile because whether a clone had refreshed a given render was situational, so a stale copy could linger. **The new rule: after the push, main regenerates its OWN renders from its OWN committed tip** - a render in main is a pure function of main's code, so it can never be a stale copy. `sync-with-main.sh render-sync` (folded into `done`) runs it:
     - It invokes [`pipeline/render_cache.py`](../.claude/skills/diagram/l7r/diagram/pipeline/render_cache.py) against main's pool under the sync lock, with `GM_ASSISTANT_ALLOW_MAIN=1` so the engine's main-tree guard stands down for this ONE sanctioned regen-in-main. Each generator runs from its OWN directory (the Mode A cwd trap), and the raster is the generators' own resvg call, so no separate render command is needed. After the regen it also rewrites `pool/index.html` (the browsable pool index, `pipeline/pool_index.py`) - derived and gitignored exactly like the renders it embeds. The CLONE gets its own copy too (GM 2026-08-27): `sync-in` on both branches runs the skill's `make pool-index-if-stale`, which rebuilds only when a manifest, render or notes file is newer than the index, so the GM can browse a clone's work in progress at `.clones/<name>/.claude/skills/diagram/pool/index.html`.
     - **The regen is unconditional but cheap**, because it short-circuits on a content hash. Every derived (Mode B) svg is stamped `<!-- render-cache: <sha256> -->`, where the hash covers that map's `gen.py` source AND the shared engine sources. render-sync skips any map whose stamp is fresh and whose png is present, and re-runs the rest. So it is self-healing (main re-derives correct renders from tip regardless of history - even after a crashed prior session) yet a push that changed nothing a map depends on costs ~0.3s; an engine change restamps every map and does the full ~30s refresh. Mode A magistracy plans (tracked svg source, only the png gitignored) are exempt from the cache: they always re-run and reproduce their tracked svg byte-identically (never stamped - a comment would dirty a tracked file), so their gitignored png is refreshed each time. This is the whole reason the old TIP-GUARD / last-writer-wins / byte-verify dance is gone: regenerating whatever tip main currently holds is always correct, and a redundant run just finds every stamp fresh and skips.
     - This is the ONE sanctioned write into main's tree, and it is now the ONE place a session runs generators against main - held under the lock, so it cannot race another session's push-to-checkout. If the regen leaves any TRACKED pool file dirty (a `.json` manifest or a Mode A `.svg`), a generator is nondeterministic: render-sync warns loudly and you must investigate (a dirty tracked file also blocks the next session's `updateInstead` push). Do not hand-copy renders and do not run generators against main by any other path.
- **Main is the integration point, never a workspace: the ONLY thing a session runs in main's tree is render-sync (step 5).** No other generators, no tests, no writes - any other command writing into `/diagram` races with another session's mid-procedure push-to-checkout (2026-07-20: a derived-file regen run in main during another session's push produced a confusingly mixed tree). render-sync itself is safe only because it holds the sync lock and regenerates from main's own committed tip. Read-only commands against main (`git log`, `git status`, greps) stay fine. **This rule is SELF-ENFORCED**: the diagram skill (`settlement.py` import-time, which every gen/gate/test imports), the webapp rootdir `conftest.py`, and both Makefiles abort with a reminder pointing here when run from main's tree - if you hit that error, re-read this section (reload CLAUDE.md if it has fallen out of context) and rerun from your clone. `GM_ASSISTANT_ALLOW_MAIN=1` is that guard's override: the GM sets it for a deliberate main-tree run, and render-sync sets it (scoped to its one locked regen) - a session never sets it by hand for anything else. (`make serve` in the webapp is exempt - the GM legitimately serves the toolkit from main.)
- **A test predicate that reads an ABSOLUTE path is self-disabling in a clone, and it fails in the direction that looks like success** (2026-08-16, found twice the same day by two sessions independently). Every session works under `/diagram/.clones/<name>/`, so a condition like `".clones" in path.parts` is true for *every* file in the tree - it reads as "skip other sessions' clones" and behaves as "skip everything". `tests/hamletgen/test_surface.py`'s package-surface census had exactly that guard: inside a clone it censused **0 names** (with the guard removed, 50), so its contract assertion compared nothing against its pin list and passed vacuously in the only place it is ever run, hiding two genuinely unpinned consumers added by the feature that introduced the guard. The rules: match on a path RELATIVE to the root being walked, or on no path at all; and make any "walk the tree and check what you find" guard **assert that it found something**, because an empty census is indistinguishable from a clean bill of health. The main-tree guards (`settlement._assert_not_main_tree`, `webapp/mainguard.py`, the Makefiles' `guard`) are the legitimate exception - inspecting the absolute path IS their job, and each is tested against synthetic paths rather than the one it happens to be running under. **Cheap detector: run the suite once from a checkout OUTSIDE `.clones/`** (a throwaway clone under your scratchpad works; the Makefile's main-tree guard only rejects paths under `/diagram`, so a `/tmp` checkout runs fine) after any change to how the suite discovers files. Two sibling failures of the same class, both found the same day: a byte-identity oracle that reported IDENTICAL across 885 artifacts having run zero generators, because the scratch tree was `cp -a`'d with the committed artifacts already in it and the regen had died - so pair every "the bytes match" pass condition with a *liveness* one (regen exit code, and a regenerated COUNT equal to the baseline's); and a `.gitignore` rule written as `.coverage.*   # trailing comment`, where `#` starts a comment ONLY at the start of a line, so the whole string was one literal pattern matching a filename nobody will ever create. **Prove an ignore rule with `git check-ignore -v <a real filename>`, which names the rule that fired** - reading the file back tells you nothing, because a broken pattern looks exactly like a working one, and copying an existing rule's shape proves less still (that one had been inert for some time, which is how it got copied). The common thread across all three: each guard PASSED, each failed in a different way - matched nothing, compared a stale baseline against itself, matched an impossible filename - and each was "verified" by reading code rather than by watching it fire. Break the guard deliberately, watch it complain, put it back.
- **Gotchas:** keep `pytest`/`ripgrep` scoped to the working dir (git ignores `.clones/`, but those tools do not read `.gitignore`, so a repo-root `pytest` would double-collect every clone's tests). Self-contained features (e.g. `/diagram`) run fully in the clone; a feature that needs `/host-l7r-repo` or `development-secrets.ini` still reaches them by absolute path - only repo-relative paths shift into the clone.

## Concurrent sessions: coordinating spec-kit feature numbers

(GM 2026-09-07, feature 197.) The GM routinely runs several sessions at once, and every session allocates its own spec-kit feature number. Numbers are a shared sequence, and the sequence is handed out by ONE tool under ONE lock - so allocation is claimed, never computed by hand and never negotiated:

1. **Claim the number with `make claim SLUG=<kebab-slug>`** from your clone (the root Makefile forwards it; `PEEK=1` looks without claiming). `scripts/claim-feature.py` takes `flock` on `<mirror>/.specify/feature-numbers.lock` and, holding it, reads every place a claim can exist: the mirror's `specs/`, the mirror's fetched `origin/main` tree, **every clone's `specs/` under `<mirror>/.clones/`** - the unpushed claims of the other sessions, which the 2026-08-16 protocol below could not see - and its own ledger `<mirror>/.specify/feature-numbers.jsonl`. Next = the maximum + 1. It creates `specs/NNN-slug/` in your clone BEFORE releasing the lock (the directory is the claim; the next caller's scan sees it), appends the ledger row (number, slug, clone, time), writes `.specify/feature.json`, and prints the directory name with `export SPECIFY_FEATURE=...` and `export SPECIFY_FEATURE_DIRECTORY=...` for the rest of the chain. Refusals, exit 2 with nothing created: run from the mirror; a slug that is not `[a-z0-9]+(-[a-z0-9]+)*`; a slug already in use anywhere the scan reads; the lock held past 30 s (a hung claim, named by file). It warns about a number main holds twice and never renumbers on a claim - see the precedent note. When the GM rules that a duplicate should be resolved (as they did for 195 on 2026-09-07), `make claim RENUMBER=specs/NNN-slug` moves that directory to the next number under the same lock, `git mv` staged, with a `renumbered_from` row in the ledger; the session then rewrites every reference to the old number. The lock, the ledger and every clone are on the host volume, so nothing needs regenerating on a fresh container; the ledger is a record and a safety net, not the only source - if it is lost, the scan still gives the right next number except that a number claimed and then abandoned (directory deleted before any push) may be reused, which identifies nothing and costs nothing.
2. **Commit and push the claim once `spec.md` exists.** The moment `/speckit-specify` writes `specs/NNN-slug/spec.md`, commit that directory in the clone and run `scripts/sync-with-main.sh push`. This is a sanctioned mid-feature push at a natural milestone - the spec is a complete, reviewable artifact even though the feature has barely begun. Note what this step is FOR now: the claim is already visible to every session on this host through the clone scan, so the push does not create the claim - it publishes it to the GM's laptop and to GitHub, where the tool's scan cannot see. The locked pull+push is still atomic: either your `specs/NNN-slug/` lands in main, or the pull surfaces a competing `specs/NNN-*` first.
3. **On collision, the unpushed spec renumbers - and this is now the fallback for ONE case.** The lock cannot see a spec authored outside the container and pushed to GitHub between the last `sync-in` fetch and your claim. If the pull surfaces one: `git mv specs/NNN-slug specs/MMM-slug`, update BOTH `SPECIFY_FEATURE` and `SPECIFY_FEATURE_DIRECTORY`, re-commit, and re-run the push. A collision between two sessions in this container is a bug in the tool, not a case for this rule - report it. (`.specify/feature.json` is gitignored since 2026-08-16 and needs no attention - it is per-workspace state that used to be tracked, and a peer's copy silently outranked `SPECIFY_FEATURE` when spec-kit resolved `FEATURE_DIR`; `scripts/clone-sync-hooks.sh` warns if it is ever re-tracked; `make claim` writes it for you.) Nothing else references the number that early, which is the whole point of claiming at specify-time rather than at feature-end.
4. **Why not peer messaging.** Sessions CAN talk to each other (`ListAgents` to see who is live, `SendMessage` to reach one), and a message carries only its own text - no session context is shared, so it is cheap. But coordination-by-chat requires the other side to be listening: a busy session replies on its own schedule, a finished session never, and tomorrow's session was not there to hear the agreement. The claim-through-main protocol needs zero cooperation and binds sessions that do not exist yet. Save messaging for genuinely conversational questions between live sessions ("are you mid-rewrite of `hamletgen.py`? I need to touch it") - not for allocating from a shared sequence.
5. **Nothing else needs active coordination.** File-level integration is already covered by this document's machinery: the locked pull+push, the overlap advisory (exit 3), and the sync-in gate rerun. Two sessions editing the same file converge through merges, not conversation. Spec numbering was the one shared resource with no guard; since feature 197 it has one - the lock - and `make audit` lists every number it has handed out.

## The clone rules in full

*CLAUDE.md keeps the normal path in a few lines; this is the record with the GM's rulings - the
stray mirror commit and its recovery, the `git -C` habit and the hook that was priced and declined
for it.*

- **Clone name = this session's name, kebab-cased.** Resolve it - do not guess: the hooks read it from the LAST `{"type":"custom-title"}` record in this session's transcript (`~/.claude/projects/<cwd-mangled>/<session_id>.jsonl`, the `session_id` being in your scratchpad path), falling back to `~/.claude/sessions/*.json`; do the same by hand. The transcript is the reliable source: `/clear` mints a NEW `session_id` and re-emits the rename there before your first prompt, while the sessions json is rewritten asynchronously. `diagram` (this repository's own name) and `gm-assistant` are FORBIDDEN clone names; an unnamed or auto-derived session has no valid workspace, so ask the GM to `/rename` it before doing repo work.
- **Create it with** `git clone /diagram .clones/<session-name>`. Repo-local config does not copy, but nothing is set by hand: `sync-with-main.sh` establishes the committer identity (from the GM's shared `~/.claude/gitconfig` - one name and address for every container, GM 2026-08-27; main's tip author is only the fallback when that file is absent) and main's `updateInstead` on every run, and `setup-dev-env.sh` does the same for main on a fresh container. Reuse an existing clone for a resumed session.
- **GITHUB `main` IS MAIN; `/diagram` IS A MIRROR.** A clone's `origin` is GitHub (`https://github.com/EliAndrewC/diagram`, HTTPS + the PAT from `development-secrets.ini` via `scripts/git-askpass-token.sh` - the procedure re-points a stale origin itself). Nobody pushes to `/diagram`; it fast-forwards from GitHub and render-sync runs there. A laptop push to GitHub main flows into the mirror and every clone like any other landing.
- **Sync in at the start of EVERY new piece of work** - `scripts/sync-with-main.sh sync-in` inside the clone (the prompt hook runs it every turn): fetch GitHub main -> fast-forward the mirror -> render-sync there -> merge into the clone. On a DIRTY clone the mirror half still runs (`sync-in --mirror-only`); only the clone merge waits, because mid-task work is sacred.

### Name the tree in the command

- **`git -C <abs-path> ...` for every git call.** No `cd` at all, and - the part that actually matters - the tree is named IN THE COMMAND TEXT, so a mislabeled section header cannot survive a re-read of what you ran.
- **One tree per command.** If you want main and a clone side by side, that is two `git -C` calls, not one `cd` and a header.

Note what this is and is not for: actually WRITING in main is already caught (the Makefile's `guard`, `settlement._assert_not_main_tree`, `scripts/main-tree-hooks.sh`). This rule prevents the quieter failure those guards cannot see - a read-only diagnostic that confidently reports the wrong tree, which is worse than an error because it looks like an answer.

**A hook was priced and DECLINED (GM 2026-08-17: "I can't think of a better enforcement mechanism either").** A `PreToolUse` hook is this project's usual answer to a recurring mistake, and it does not fit this one. A hook precise enough to catch the motivating case would have to demand `git -C` on EVERY git call - it fired on a command with one legitimate `cd` and no second path, so nothing structural marked it as wrong - and a hook that fires on nearly every correct command trains sessions to pattern-match past it, which degrades the guards that matter. The narrow alternative (fire only when ONE command contains both a `cd` to a non-clone path AND `.clones/`) is near-zero noise but would have caught neither instance, since neither named two trees. So this rule is deliberately unenforced and rests on habit; the cost is that it will be broken again. **Reopen only with a mechanism that would catch a single-`cd` command whose section header names the other tree** - that is the shape to beat, and neither candidate above does.

### No feature branches

**NO FEATURE BRANCHES - spec-kit work included** (GM 2026-07-27). Isolation already comes from the session clone; a branch on top of it is a second axis that buys nothing and broke the stop-work procedure for a whole session. Branch creation is off (`.specify/extensions.yml`, `before_specify`, `enabled: false`) and [`scripts/no-branch-hooks.sh`](../scripts/no-branch-hooks.sh) blocks a hand-rolled `git checkout -b` (escape hatch: `NO_BRANCH_OK` in the command, with a reason). Spec-kit still needs to know which feature is active: **`export SPECIFY_FEATURE=NNN-slug`**, which `common.sh`'s `get_current_branch()` returns ahead of asking git, so `check_feature_branch()` in `setup-plan.sh` / `setup-tasks.sh` is satisfied with no branch at all. **Export `SPECIFY_FEATURE_DIRECTORY` alongside it** - `export SPECIFY_FEATURE_DIRECTORY=specs/NNN-slug`. `SPECIFY_FEATURE` alone is NOT enough and the difference is silent: `common.sh` resolves `FEATURE_DIR` from `SPECIFY_FEATURE_DIRECTORY` (priority 1), then `.specify/feature.json` (priority 2), and only then from the branch name that `SPECIFY_FEATURE` supplies (priority 3) - so with a stale pointer present, `SPECIFY_FEATURE=115` yields `CURRENT_BRANCH=115` and `FEATURE_DIR=.../116`, and spec-kit writes into a PEER's feature directory while every log line looks right. `make claim` prints both exports.
