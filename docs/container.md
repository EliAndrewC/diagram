# Container: launching, fresh-container init, dependencies

*Project reference, split out of [`../CLAUDE.md`](../CLAUDE.md) so it is loaded on demand rather than in every session's context. CLAUDE.md keeps the short always-on version of these rules and points here for the full spec.*

**Load this file when:** launching or rebuilding the dev container, or something that used to work now fails with "command not found" / "No module named" / "resvg not found", or you are adding a permanent dependency or bumping the Python version.

---

**Launching the container**: prefer gm-assistant's `scripts/launch-container.sh` over a hand-edited podman command - it is the ONE copy of that script (GM 2026-08-25: it lives in gm-assistant only; this repository's copy was removed the same day). Run it from THIS repo root (`../gm-assistant/scripts/launch-container.sh`): if this repo's container is already running it opens a fresh `bash` shell inside that one (and prints the ports it has published); otherwise it starts a new detached container named `claude-<repo-dir>` (PID 1 is `sleep infinity` and every terminal - including the first - is a `podman exec` shell, so exiting any terminal leaves the container and the other shells running; it persists until `--fresh` or `podman rm -f`), mounting the repo at `/diagram` plus the host `~/.claude/` and `~/.claude.json`, and publishing/mounting whatever the repo's `CLAUDE.md` declares. Those declarations are greppable HTML comments at the top of `CLAUDE.md`: `container-workdir` (where the repo mounts - `/diagram`), `container-mounts` (HOST:CONTAINER; here `..:/host-l7r-repo`, the GM's whole `l7r` checkout - the same mount gm-assistant declares - so the setting notes the research cites are at `/host-l7r-repo/gm-assistant/setting/` and the canonical `l7r.md` at `/host-l7r-repo/setting/l7r.md`), and `container-ports` (HOST:CONTAINER - this repository serves nothing and declares none; the script notes that and publishes nothing). Mount host paths are resolved relative to the repo root (or `~`, or absolute) - the GM keeps each project repo as a sibling inside the `l7r` notes repo (`<l7r>/diagram`, `<l7r>/gm-assistant`, `<l7r>/character-sheet`, ...), so `..` is always the canonical `l7r` checkout regardless of where the tree lives. The same script works for the GM's other repos - each just needs its own directive lines. `--fresh` recreates from scratch; `--no-ports` skips publishing; `--no-claude` skips mounting the host `~/.claude*` (use it on a shared/work machine so the container does not inherit that host's default Claude account - log in fresh inside instead; `CLAUDE_SRC=/path` points at a specific config dir).

A fresh launch also does two things on its way to the shell, both skipped when attaching to a container that already exists. It runs **`claude update` inside the container** (`--no-update` skips it): the `claude` binary lives in the container's own `~/.local/bin`, *not* in the mounted `~/.claude`, so it does not persist across rebuilds and every fresh container would otherwise start on whatever build the image shipped - and `podman pull` cannot help, since the image itself is only rebuilt occasionally. And it **seeds `~/.bash_history` with `claude --dangerously-skip-permissions`**, so the first thing you do in the new container is press Up and Enter. Both steps are best-effort: they warn and continue rather than costing you the shell.

**Fresh-container init (start here on every new container)**: the container is launched via gm-assistant's `scripts/launch-container.sh` (see above) - it bind-mounts the repo at `/diagram`, the `l7r` checkout at `/host-l7r-repo` (so gm-assistant is `/host-l7r-repo/gm-assistant`), and the host's `~/.claude/` + `~/.claude.json` into `/home/agent/` so Claude Code auth, preferences, agents, skills, and per-project memory (under `~/.claude/projects/-diagram/`) all persist across container rebuilds. `/host-l7r-repo/setting/l7r.md` is the canonical the setting notes derive from; this repository reads the derived notes in `/host-l7r-repo/gm-assistant/setting/` and never edits the canonical. Once you're inside, run **one command** from the repo root:

```
container-scripts/setup-dev-env.sh          # install everything missing, then verify
container-scripts/setup-dev-env.sh --check  # verify only (~3s, no network) - is this container healthy?
```

That installs the apt packages (`resvg` + the DejaVu faces the diagram renderer needs) and both pip lockfiles, then proves each one works rather than assuming it. (Since the split, feature 131, there is no Playwright browser to install here - the webapp and its screenshot suite stayed in gm-assistant, and this repository's first fresh container found the script still installing from `webapp/requirements.txt`, a file that does not exist here.) Run it on every fresh container, and run `--check` the moment something that used to work fails with "command not found" / "No module named" / "resvg not found" - a container rebuild keeps only the bind-mounted repo and `~/.claude`, so a rebuilt container looks subtly broken until this has run. (Real cost of not having it, 2026-07-25, in gm-assistant: a rebuilt container had silently lost `resvg`, and the failure surfaced as three mystery test failures a full gate run into a feature.)

After that, from a session clone's `.claude/skills/diagram/`, `make quick` and then `make done` should pass (ruff + format + mypy --strict + pytest + coverage). On a FRESH clone run `make map` first: the pool's live renders are gitignored, so a fresh checkout has none, and the two tests that read them (`test_every_live_pool_png_matches_its_own_svg_viewbox`, `test_crown_fills_covers_every_recorded_crown`) report that they had nothing to check rather than pass vacuously. `make map` regenerates the reference hamlet with its render (~30 s) and they have their artifact.

**INSTALL WHAT YOU NEED - never work around a missing dependency.** This container has **passwordless sudo** precisely so a session can `sudo apt-get install` anything it wants without asking, and pip installs are equally free. Adding a dependency is a normal, cheap decision here, not a last resort: if a library would make an approach simpler, faster, or more correct, install it and use it. Never reject a design *because* the dependency is not currently installed - that reasoning is invalid in this repo. (When a new dependency becomes permanent, add it to `.claude/skills/diagram/requirements.in` / `requirements-dev.in`, re-lock, and add a check to `setup-dev-env.sh` so the next container gets it too. A one-off exploratory install needs none of that.)

`container-scripts/` holds things that run INSIDE the container; `scripts/` holds things that manage the host-side clone/main relationship (`sync-with-main.sh`, the hooks). Anything in `container-scripts/` may freely `apt-get install`; it refuses to run outside a container so it cannot spray packages across the GM's laptop.

Runtime and dev deps are split into two lockfiles beside the skill's `pyproject.toml`, in `.claude/skills/diagram/`: `requirements.txt` (shapely, pillow - what the engine imports) and `requirements-dev.txt` (ruff/mypy/pytest/pytest-cov/pytest-xdist/types-shapely/pip-tools - the gate). Both were pinned at the 2026-08-25 split to the versions gm-assistant's lockfiles carried, so every recorded green gate ran on exactly this set; a re-lock that bumps ruff or mypy can change what the gate reports and is a change to review, not housekeeping. Both target **Python 3.14**, which is what ships in the dev container (`docker.io/docker/sandbox-templates:claude-code`); the version is also pinned in the skill's `pyproject.toml` (ruff `target-version`, mypy `python_version`). Re-lock either file with `pip-compile --upgrade --output-file=<file>.txt <file>.in` from that directory (sources are `requirements.in` and `requirements-dev.in`). If you bump the Python version, update pyproject.toml and both lockfiles together - they're meant to stay aligned.

**What is deliberately NOT here** (feature 131): the webapp, its Playwright screenshot suite, its Fly deployment and its port/server-binding rules all stayed in gm-assistant with the webapp - see that repository's `docs/container.md`. The one cross-repo fact that still matters here is the `l7r` namespace: `.claude/skills/diagram/l7r/` is a PEP 420 namespace portion that shares its parent with the webapp's `l7r.app` when both are on one `sys.path`, which is why it must never gain an `__init__.py` (`tests/test_namespace_portion.py` guards it).
