# The pool: the frozen legacy maps, the migration, and scripted generation

**Load this file when:** You are about to touch a pool map, convert one to scripted generation, work on `hamletgen/`, or you found a rule violation on a hand-authored map.

The short always-on version of each rule is in the engine index, [`l7r/diagram/CLAUDE.md`](../l7r/diagram/CLAUDE.md).

## TWO TREES, AND WHICH ONE A MAP GOES IN (feature 161, 2026-08-30)

The pool is two sibling trees, each `<tree>/<tier>/<map>/` - one folder per map, holding that
map's whole bundle (`<map>.gen.py`, `.json`, `.notes.md`, and its renders).

| | `pool/` | `legacy-hand-authored-pool/` |
|---|---|---|
| holds | the LIVE maps: the scripted hamlets (`hamlets/`), the Mode A magistracies (`magistracies/`, one of them the `ochiba-roundtrip-test` sheet) and the country shrine (`country-shrines/`) | the 18 FROZEN hand-authored Mode B exhibits |
| regenerated / re-gated | every run | **never** |
| renders in git | derived, ignored (a hand-drawn Mode A `.svg` is the exception - it IS the source) | ignored too (feature 178, below) |
| `poolmaps.classify()` | `scripted` or `compound` | `legacy` |

**What decides the tree is `classify()`, not the tier.** `hamlets/` exists in both. The two axes are
independent and conflating them is the mistake this layout exists to prevent: the magistracies
are hand-authored AND live, because a compound plan is small enough that scripting it buys nothing
(`docs/migration-plan.md` section 1). "Live" is not the opposite of "hand-authored".

**WHEN A MAP IS CONVERTED, MOVE ITS FOLDER**: `git mv legacy-hand-authored-pool/<tier>/<map>
pool/<tier>/<map>`. The ignore rules are per-tree patterns rather than per-file exemptions, so
nothing else is added or deleted.

**No generated render is tracked, anywhere** (feature 178, GM 2026-09-03: *"in general, the generated html pages
should not be tracked just like the generated svg and png files should not be tracked"*; on the frozen exhibits,
*"I don't see why we should be tracking those renders."*). A live map's renders rebuild with
`make map GEN=pool/<tier>/<map>/<map>.gen.py`; the tracked source is the `.gen.py`, `.json` and `.notes.md`, plus the
`.svg` of a tier `l7r/diagram/buildings/types.json` declares hand-drawn (`tests/test_building_types.py` holds `.gitignore` to that
declaration). Never commit a live map's svg/png.

**Everything that walks the pool asks `poolmaps.bundles()`**, saying which tree(s) its job concerns
(`contracts/pool-discovery.md` in `specs/161-pool-per-map-folders/` has the per-consumer table). Do
not write a new glob: ten consumers once hardcoded the shape independently and they drifted - a map
regenerated by `regen.py` that `make maps` never rolled. The tree argument is the load-bearing one,
because getting it wrong is SILENT: a sweep over too few maps is green. A new scripted engine is added to
`poolmaps.SCRIPTED_ENGINES`, or a gen built on it is invisible to the classification.

## The legacy pool is FROZEN (GM 2026-08-16)

Every hand-authored Mode B map - 8 hamlets, 4 villages, 3 towns, 3 provincial cities - is a
permanent EXHIBIT: never regenerated, never re-gated. They stay in `pool/index.html` (which covers
both trees on one page). `pipeline/poolmaps.py` is the classification (scripted / legacy / compound),
shared by the gate's pool sweep, by `pipeline/regen.py` (which prints `FROZEN` and skips; `--frozen-ok`
overrides for a deliberate, GM-sanctioned re-render) and by `tools/cache_audit.py`.

WHY: hand-authoring is deprecated (the freeze decision is recorded in full in `docs/migration-plan.md`
section 2), so every hour spent re-fitting a legacy map to a new placement rule, and every engine
change flag-gated to hold the deprecated compositions byte-identical, was payment on a process
being replaced. The fix for a frozen map that violates a post-freeze rule is CONVERSION, not
retrofit - do not "fix" a frozen map, and do not treat its rule violations as bugs.

The consequences, so nobody rediscovers them one gate failure at a time:

- **Engine changes need no byte-identity flags.** Change behavior freely; the scripted
  cohort and the gate hold the line, and a new rule ships un-gated by `meta.generated_by`.
- **Coverage is 100% on every module**, the above-hamlet wings of the `settlement/` package included
  (towns, cities, the capital), though nothing rolls them until their tiers convert.
- **Frozen manifests remain legal READ-ONLY fixtures** (citybudget prices the tango/nagahara programs) -
  frozen bytes never change, so those tests stay green forever. But never write a test that RUNS a legacy gen
  or expects a frozen manifest to PASS the evolving gate: either one re-shackles iteration to the deprecated pool.
- **The pool's committed artifacts must stay clean.** Any test or tool that runs a live gen for
  its own purposes (the randomness ratchet, the gencache round-trip) must leave the committed
  bytes exactly as it found them - byte-restore, not re-run, because the engine may have drifted
  since the artifact was committed.

## MIGRATION: new rules land in the SCRIPTED path first, and legacy maps inherit them on conversion

GM 2026-08-13, on finding that threshing yards sit in their neighbors' shadow pool-wide: *"rather
than try to fix our existing maps manually, we'll document the decision to NOT fix this specific map
feature on our manually generated maps, but we'll fix this kind of thing in our generation scripts
and thus ensure it will be fixed as we convert our existing maps to be generated by the new scripted
process."*

**What this costs, and say it out loud when you use it:** the pool is PERMANENTLY inconsistent until
conversion, the accepted trade recorded in `docs/migration-plan.md` section 2, and the gate will not tell you
which frozen maps are behind. Record the measurement at the point of decision - the sun rule's entry on
`research/contents.json#homesteads` lists every affected map and by how much - so a reader can see the size of the
debt rather than discover it. Reach for this when a rule is right but re-packing the pool is the wrong trade, never to
avoid fixing a live map that is simply inconvenient.

## Scripted generation - read before touching `hamletgen/`

The project has committed to scripted generation (GM, 2026-08-15). The standing plan -
what is converted, what order the rest goes in, the bar a conversion has to clear, and the measured
iteration budget - is [`docs/migration-plan.md`](../docs/migration-plan.md). **Update its status table as part of
finishing any conversion.**

[`hamletgen/`](../l7r/diagram/hamletgen/) is the generator, a package whose
[`CLAUDE.md`](../l7r/diagram/hamletgen/CLAUDE.md) says which submodule holds which stage, so **load the one stage you
need rather than the whole engine**; a map is rolled with `make map GEN=...`, a one-off hamlet with `make hamlet ARGS=...`. [`pool/hamlets/`](../pool/hamlets/)
holds its maps (`meta.generated_by` marks a scripted map). A session drawing anything but a hamlet still follows the
specifications on its tier's research page (`research/contents.json#tiers` and the topic pages beside it). The lessons
the experiment left are in [`lessons.md`](lessons.md).

**A shared registry the placer reads must be written by every builder.** `draw_comb_field` once appended its dry hem
only to `block_polys`, never to `s.dry_polys` - the registry the grove, lane and threshing-yard filters read - so its
hem plots stopped a house and not a tree. Same shape as "placement and its check must read the SAME manifest source",
in [`gate.md`](gate.md).

**A cohort is a much stronger test bed than a map.** Twenty hamlets rolled from consecutive seeds and gated caught ten
distinct defects - an intake at mid-slope starving the fan, a pond laid over the crop, a cluster seated inside a
CONCAVE field margin (the outward normal was taken from the centroid, which is only right for a convex polygon), a
supply canal's tail dying in bare ground, a brook turning through an acute hairpin, and two engine bugs. Authoring one
map meets perhaps two of them. If you add a placement rule, run it against a cohort, not against the map that
motivated it.

**MEASURE THE COHORT'S BASELINE FIRST - the number you are aiming at is not 24/24.** A cohort carries pre-existing
failures, so a bare "16 of 24 passed" read against nothing cannot tell a regression from the weather. Roll the SAME
seed range on unmodified code before judging your own - and note that any change altering how many draws a gen takes
re-rolls every map, so the residue ROTATES rather than shrinking in place: same pass rate, different maps, possibly
strictly less broken - which only the side-by-side shows.

**But "rotated" is not a defense** (constitution XIII). A seed that passed before your change and fails after it is a
REGRESSION, however much else improved - and nothing merges carrying one. Where the re-roll genuinely destroys
per-seed comparison, the bar is that the pass RATE must not drop AND every newly-failing check is individually
diagnosed. Take the baseline in a detached worktree (root `CLAUDE.md`), never by stashing: a stash once reverted
`inashiro.json` underneath a `settlement-review` agent reading it - anything handed to a review agent is LIVE for as
long as the agent is.
