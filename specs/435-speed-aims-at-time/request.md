# Feature 435 - the GM's request, verbatim

The GM, 2026-10-27, after the call-count breakdown (feature 434):

> Okay, now, before we do anything, I want to make sure that we don't inadvertently incentivize some really bad behavior in which we replace function calls with loops inside of a single function, which does not actually save anything. like, we have a checklist-based process for these automations and such, and we are trying to actually make things take less time, not merely decrease the number of function calls. Like, the function calls are a good proxy for that, but you know the old rule that the moment you begin measuring one thing and not a different thing, then you might end up accidentally optimizing for the one thing at the expense of the thing that you really care about. So are we 100% sure that everything that we are doing with this feature is geared towards reducing function calls in order to achieve the goal of taking less time, and that we are at no point going to fall into some kind of trap in which we begin doing big refactors that decrease the function calls without actually affecting the time at all? like combining multiple functions into a single function in order to decrease the number of function calls is pointless. Do we have checklists that are used for this kind of optimization? Should we? Should that be the next thing that we do, in which we kind of have a process for improving our performance? Because this is not the last time that we are going to have to do that. I think that that is a task that we will come back to again and again, not just as we optimized our hamlet generation, but then when we move to villages, and then when we move to towns, and then especially once we begin building walled cities, where we will have to place things along city streets, and the number of buildings being placed will increase from dozens to hundreds. And then eventually, literally, to thousands. So I think that we need some kind of checklist-based process to make sure that when we are optimizing, we are optimizing for the correct thing. And like, we should also be looking at the amount of time that things take, even if that's not the thing that we are recording in this specific document, you know? because the function calls do not vary based on the system load, whereas the time does. So that's a good reason to record function calls here, but we need to be really confident that we don't do anything silly and optimize the wrong thing, right? What do you think a good way forward is in order to keep our goals centered on that not just in this one Claude Code session, but as we continue to optimize this project generally?

The session measured (an alternating best-of-3 A/B of the engine before feature 417's speed lane against HEAD: calls -38% to -44% and time 0% to -6% at 40 households, calls -32% to -35% and time -10% to -16% at 20) and proposed a feature. The GM:

> So to be clear, I don't want timings to be a gate anymore. I am not reversing the rule that timings gate nothing. Because the problem that we keep running into when we use timings as a gate is that when the system is under load, the timings change significantly. The timings change based on which of our CPUs we get access to, because not all of the cores on this host run at the same speeds. And then when we have to wait for a window when the host is not busy in order to take accurate timings, it slows us down rather than speeding us up. So I want to be very clear that timings are not a gate, but improving timings is the goal of any performance improvement ticket. And so the checklist should take that into account when making performance adjustments. Does that make sense? like, we should not have a high degree of confidence that whatever time we measure is going to be replicated across different runs under different circumstances, etc. But we can look at the totality of what we have done and generally find that time will go down when making comparisons under similar circumstances. And if time going down seems to correspond to function calls going down, then so much the better. But we are not gating on specific amounts of time, or on timing increases, or on particular timing decreases.
>
> Do you feel like you're able to capture the sensibility that I am expressing? I mean, I am kind of presuming that we can simultaneously use a checklist-based approach while also applying good judgment. Such that the checklists serve the function of helping us not forget steps as we work towards our goal, rather than the checklist items being taken as if they are themselves the goal. Do you feel like you are able to incorporate this into the next step when you do it? Don't actually start yet, because I want to make sure that we have this down before we move forward.

The session restated the sensibility (time the goal, never a gate; calls the deterministic measure; time evidence read with judgment across the totality; the checklist a memory aid, not the goal) and the revised proposal. The GM:

> Okay, in that case, yes. Start off by doing this, by creating these checklists as the next item in the spec, and then working through reverting some of the changes that you made before that reduced call counts without actually improving performance, because they were done by falling into the exact trap we are trying to avoid. Then after that, please proceed with the three cheat fixes. I am going to lunch, so hopefully by the time I get back, then all of this will be done, and we will have new numbers that I can look at as we decide what to focus on next in our performance improvement efforts after this is done and the three cheat fixes are done. Thank you.

("cheat fixes" is dictation for "cheap fixes": the three items feature 417 T57's analysis ranked first - the notice board's seat screen, the homestead bundle geometry built once, the wells' feasibility mask.)
