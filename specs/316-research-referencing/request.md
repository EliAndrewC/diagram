The session answered (summarized here, not the GM's words): build it, as the code-side twin of feature 311's owed
record checks and `entry-drift`'s verdicts, with feature 227's docstring-generated walk-through as the proof. (1) A
`Research:` section in docstrings, ONE LINE PER CLAIM (the dry-field example is four claims: count, size, placement, share),
each naming a question pointer or a class (GUESS, CONVENTION, DEVIATION, or no physical claim); constants carry the same in an
attribute docstring; a gate test requires the section on everything in scope, as the `Steps:` test does. (2) A committed
ledger, one row per (function, claim): a hash of the function's code with docstrings and comments stripped plus the
constants it reads, a hash of the cited question's text, the verdict and the date; either hash moving owes the row again.
Callee changes are not followed - stated as the limit. (3) A new Opus check, `impl-drift`, from a bundle: IN-STEP, DRIFTED,
NEEDS-RESEARCH, MISLABELED, and a flag on a function that decides something physical but claims nothing. (4) The walk-through
page renders each step's `Research:` lines as links into the built record. (5) Scope: the hamlet generator plus the written
procedures for the magistracy and the country shrine (markdown, a per-section marker); the hand maps themselves stay out. The
first sweep is "everything owed", batched one agent per stage. It recommended a new feature number with 296 closed as
superseded and its two findings seeded as the first DRIFTED rows; at the push, an owed row blocks, a DRIFTED row the change
introduces blocks, and a pre-existing DRIFTED row is a warning in a report; and per-claim rather than per-function or
per-area.
