# The GM's request (verbatim, 2026-09-26)

The first message, asking what it would take:

> How much effort would it be to create clickable user interactable versions of the magistracy maps that tie into our research? for now, I only want to tie into existing research findings that already exist, rather than doing new research findings, although a big bonus to having the interactive map, as we do, is that it becomes much easier to have me look at things and then see whether our research is spotty and needs more citations and such. But for right now, I would mostly be interested in being able to highlight things like the outer courtyard versus the inner courtyard and see write-ups of what these things were and the extent to which this is indeed based on real historical research or is a thing specific to this fictional setting. For example, the Vermilion Threshold Stones in the Ochiba Magistracy are specific to our fictional setting, whereas the outer courtyard where hearings were held is based on real historical research, if I remember correctly. That kind of thing.
>
> We already have interactive maps for our hamlets, and the goal is to have all of our scripted maps be interactive in that way. However, this does raise an interesting question, which is whether or not the addition of interactive maps becomes something that pushes us towards wanting our magistracy buildings to be scripted. In the past, we have kept them not scripted because the amount of variation in buildings at the level of detail that we are able to render is much greater than the level of variation that we need to be able to display in a zoomed out settlement. And therefore a scripted process is likely to constrain us by making it too difficult for us to represent things that we want to represent. That logic seems sound, but we should take care to not create a process by which we are by hand making the same changes in multiple places.
>
> offhand my instinct is that the interactive map therefore is generated by a script which consumes the hand-drawn map as an input. Since what we are consuming is SVG or something then this is probably doable. Or maybe the script that generates the SVG is also generating the interactive map. Either way, the main important thing is that the labels and the features on the building diagram for each magistracy have a common source, such that changing that source in one place is enough to change it downstream. And then since we already have annotations on what things are, then it should be relatively easy for us to have the interactive map automatically draw from and render those.
>
> I am not trying to dictate implementation here, and in fact, I want to make sure that we don't jump into the wrong implementation before we really get started. So, at a high level, what do you think about all of this?

The session's answer proposed: tag the hand-drawn SVG itself (`data-kind` attributes, which resvg
ignores), one shared registry of Mode A kinds written from the existing `research/buildings/` entries
(What / Why / classification / Entry, map particulars such as the threshold stones as per-map kinds,
`buildings/types.json`'s required features folded in rather than kept beside it), a script that reads
the tagged SVG and writes the page through the existing interactive-page machinery, run from the map's
`.gen.py`; a test that every drawn element carries a known tag. Magistracies stay hand-drawn.
