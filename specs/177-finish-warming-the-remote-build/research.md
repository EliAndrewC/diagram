## R2 - Why `hooks-test` runs in full on every build

`make done`'s phase loop skips `hooks-test` when `gate-stamp.py --fresh hooks` says the guard scripts
are unchanged since the last green run. Both pieces of that state live under the git directory:

- `<git-common-dir>/gate-green-hooks` - `hash_files(scripts/*.sh, scripts/*.py)` salted with
  `GATE_RECIPE` (`gate-stamp.py`, `_stamp_path`);
- `<git-common-dir>/hooks-test/<guard>` - per suite, `sha256sum` of that suite's DERIVED dependency
  set (`_hookdeps.py`), written by `_hookrun.sh` when the suite goes green.

A CodeBuild container clones fresh, so it has neither, and the log says so in as many words:
`21 guard suites green, 0 unchanged since they last went green`. Locally the same phase is normally
0 s. Nothing about the state is machine-, clock- or clone-derived - it is a hash of file CONTENT -
which is what makes carrying it between builds safe, and is the same property 175's A2 relied on for
the gencache key.

**The safety property to preserve**: only a state a BUILD wrote may be restored, because the S3 cache
is populated by the build and never by a laptop. A remote gate then skips only what a remote gate
proved.

## R4 - What may be excluded, and the one path that says NO

This is the FR-005 derivation, in progress. Findings so far:

- **`wip/` renders**: nothing in the gate reads them. `render_cache.engine_fingerprint` and
  `gencache` both PRUNE `pool/` and `wip/` from their walks; the only `wip/` path any gate phase
  touches is `wip/shiro-daika.gen.py` and `wip/shiro_daika/*.py`, which `check-file-scale.py` and
  `ruff` scan - **so the `.py` stay and only the `.html` go**.
- **`dev/placement-stages/`**: a documentation artifact regenerated by
  `make placement-stages`. No test reads it; `dev/placement.md` links it for a human.
- **legacy `.svg` / `.png`**: **NOT freely excludable.** `tests/test_villages.py` (the raster-versus-
  viewBox agreement test) walks `poolmaps.bundles()` across BOTH trees, and for every **hamlets**-tier
  bundle where `.svg` AND `.png` are both present it asserts the PNG's pixel height matches the SVG's
  viewBox. Its `continue` for a missing render is deliberate ("a LIVE map's renders are gitignored; a
  clean checkout simply has none"). The legacy hamlets' 97.9 MB therefore STAYS. The other legacy
  tiers (73.6 MB) are still open: no reader has been found yet, and FR-006 says an unproven exclusion
  does not happen.

  **CORRECTION, round 2 of the spec review.** This paragraph first said that sparsing the frozen
  exhibits out *"would not fail, it would make the test silently check nothing"*. That is wrong, and
  the reviewer read four lines further than its author did: the test ends on

      assert checked, "no hamlet render to check in EITHER tree - the frozen exhibits' renders are
      committed, so this should never be zero in a real checkout..."

  so a TOTAL exclusion fails loudly, by name. **The real hazard is PARTIAL exclusion**, and it is
  worse than the one first described because it is invisible: `checked` only has to reach 1, and
  there are EIGHT frozen hamlet exhibits (`akagahara`, `enokida`, `honda`, `ikegami`, `moritono`,
  `shimizu`, `tanada`, `yatsuda`), so dropping seven of them passes green having checked one map.
  The conclusion - these renders stay - is unchanged; the reasoning that gets you there is not, and
  the corrected version is what FR-005's "a green build is not the proof" clause now rests on.

Candidate set on the evidence so far: `wip/*.html` (190.8 MB) + `dev/placement-stages/**` (78.4 MB)
= **269.2 MB of 465.8**, with a further 73.6 MB pending proof.

## R6 - The cache-location collision (found while reading R5)

`cache/` holds **one** object, not two, and the phase records say why: the green reference gate
(04:43) and both `TARGET=tripwire` operations (04:52, 04:57) all ran with

    cache = {"type": "S3", "location": "gm-assistant-ci-130071571821/cache/gm-assistant-check/reference"}

`dispatch.cache_location(bucket, project, scope)` keys on the SCOPE, and an operation's scope is
still `reference`, so a tripwire's cache overwrites the gate's and vice versa. 175's D2 bounded the
object count at four and got that right; what it did not foresee is that two runs caching DIFFERENT
content share one of those four.

**Blast radius: performance only.** The gencache key is content-derived (175's A2), so an entry
written by a different run can only MISS - it can never serve a wrong answer. The cost is a cold
build that thought it was warm. This is one of the three diagnostic failures the 2026-08-31 session
listed as "cache collision"; it was seen and not fixed.

## R8 - The guard defect, reproduced

`scripts/main-tree-hooks.sh` refuses a WRITE while the session's cwd is inside main's tree, unless
the command first `cd`s out. That "cd out" is found by:

    LEAVES=$(printf '%s' "$SCAN" | grep -oE "(^|[;&|]|&&)[[:space:]]*cd[[:space:]]+\"?[^\"[:space:];&|]+" | tail -1 | ...)

The command-position alternatives are start-of-string, `;`, `&`, `|` and `&&`. **`(` is not among
them**, so in

    ( cd /diagram/.clones/<name> && cat > file )

the `cd` does not match, `LEAVES` is empty, the guard concludes "no cd at all - the command runs where
the session stands", and refuses. That is the exact form the refusal message itself prescribes:
*"`( cd <your clone> && ... )` in a subshell for anything you want to DO."* Reproduced four times
in this session before the workaround was found. The bare form `cd <clone> && ...` is accepted,
which is why the defect survived: it only bites a session that follows the advice.
