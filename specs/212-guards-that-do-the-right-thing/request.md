# Feature 212 - the GM's request, verbatim

The GM opened the session "Diagram hooks" on 2026-09-07 with this. The two guard messages they
quoted are elided at `[...]`; they are `scripts/make-only-hooks.sh`'s bare-pytest refusal and
`scripts/pair-hooks.sh`'s gate-without-review refusal, as those scripts printed them that day.

> I'm looking at some of the hook failures that we have gotten recently. I mean, I say failures, but what I really mean are times that our hooks have prevented us from running a particular command. In the past, we seem to have gotten quite a lot of good savings out of using hook context, which is to say having our hooks not necessarily fail, but warn the Claude Code session about what is happening and about what would be a failure while also either having the command succeed and then fail on the next attempt or even, in some cases, rewriting the command so that it does the thing which we infer was intended. from looking at some of our recent failures, I feel like there are additional opportunities for us to do this. For example, I recently saw this in a different session:
>
> [...] BLOCKED: pytest run directly rather than through make. Everything here goes through a make target, so an expensive run can ask whether the cheap one would do first - and a filter, a coverage flag or a second path is a shape this hook will not rewrite for you. [...]
>
> Now, of course, it is good that we do not allow pytest to be run directly because allowing it to be run directly has, in the past, resulted in very, very long pytest runs that were not necessary. However, if A Claude code session is using Pytest to run a targeted set of tests, such as targeting a specific module or even a specific test case, then rather than failing, that does seem like something where we could modify the command so that instead of running Pytest directly, we translate it into the make target which should have been run, and then we pass back additional hook context to the session explaining what we did and instructing the session to do the correct thing in the future. This will save time. It might not always be applicable, but I think we can look at the past failures and see whether it is. For example, I believe that we are already logging or at least Claude Code is already logging. All of the times that any of our hooks reject a command including what the command was. Therefore, we should be able to look at whether an attempt to run pytest Is suitable for being rewritten in this way. Our hook could then detect whether the use of pi test is suitable or not, and if it is suitable, then we rewrite it. And, otherwise, we reject it as we reject it now. How does that sound?
>
> Along the same lines, I was looking at this failure, which I have seen a few times:
>
> [...] BLOCKED: the gate and the independent review run TOGETHER. No settlement-review is pending in this session and none is recorded for this content. [...] Start both at once instead: make verify [...]
>
> Now this is one where I am less certain than with the previous example, but it does seem to me that anytime we are able to say that a command was run incorrectly and then supply the correct thing to do, then it is at least possible that what we should do is simply do the correct thing and then inform the session through hook context that we have done it. That said, this is a case where I don't know whether this would apply or not. However, because we do log these past failures, perhaps you could look at whether the invocations which were made can reliably be translated into the command that should have been run. In which case, we can update our hook to simply do that. How does that all sound?
>
> If this makes sense, then please proceed. You can do this as a speck kit feature and then take it from start to finish. An additional part of this feature should be auditing our other hooks to see whether there are other places where we are blocking a command from being run when we could instead simply run the correct command and output hook context explaining what we did. because this is already a pattern, which seems to be working in some places, I expect it could work in others. However, I do not expect it to be able to work or be reliable in every case. So I imagine that there will always be some hook commands which simply fail. Determining this would be the point of the audit, and then part of the feature is acting upon the results of that audit if there are any other easy wins to be made along these lines. Thanks.

## Appendix - a task added at the GM's request, relayed 2026-09-07

While this feature was being implemented, the session "Diagram html" relayed a request from the GM
(their own words are the one quoted sentence; the rest is that session's account of the incident):

> The GM asks you to add a task to the spec-kit feature you are working on: a guard that stops a backtick from landing inside a Makefile recipe comment. [...] On 2026-09-07, feature 207 added a recipe comment to the skill Makefile's test-full target in the project's usual form, a shell no-op line `: "..."` continued with a backslash. The comment named the target as `make test-full` in backticks. Inside a double-quoted shell string a backtick is a command substitution, so the comment RAN `make test-full`, which reached the same comment, and the target recursed 914 levels deep until the container hit its 2,048-process limit and every session's forks failed. [...] the GM's ruling is that a note is not a reliable prevention: "anytime I see a bad problem having occurred, then just commenting, saying not to do it again is not a good way to reliably make sure that the problem does not recur."
>
> What the GM is asking for: a check that confirms no recipe comment contains a backtick (or, the same hazard, an unescaped `$(` inside the double-quoted string), enforced by tooling rather than by memory. [...] Please add it as a task on your current feature rather than a new feature, per the GM.

It is FR-010 of the spec and T10 of the tasks.
