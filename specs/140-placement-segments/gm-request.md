## 2026-08-28, after feature 138 - the question

> Okay, so it sounds like the things which are currently slow are "homestead fitting, hinterland scatter, the comb solver". and other things of that nature. So let's go a little deep on that and think about what we could do algorithmically to make those things more efficient. I understand that to some extent, this can be difficult, but I do wonder whether part of what is making it difficult might be us treating certain things as being part of our algorithm that do not need to be. For example, I believe that our scrubland and marshland draws a lot of individual strokes. for things like the lone pines and the grass. And we draw a lot of individual strokes for things like bamboo. And I am wondering if what is happening that is very inefficient is that when we checked for overlaps, we might be checking for overlaps with many, many thousands of individual elements rather than checking for overlaps with one single block of area, which is the boundaries of those things. Does that make sense? I mean, the same thing goes for trees and bamboo. If what we are doing is checking for overlaps with every individual tree, then that is going to be algorithmically bad. Whereas if we know what the boundaries of the forests and copses are, then that becomes very algorithmically simple. at which point things which are taking tens of seconds to run might literally be a fraction of a second. again, I have not looked at the code, so I'm not sure. But can you take a look and see whether this is a type of improvement which could be made? I guess trees are maybe a bad example because from looking at the hamlet placement order, we are rendering most of our trees after we render the village lanes. But in general, I think my point stands. Now, admittedly, this is an example of... the branching algorithm for the village lanes. But I do think that some of our other placement algorithms could benefit from that as well. For example, if our homestead fitting is checking for overlap with individual strokes of scrubland, then that's crazy, and we should totally do something very different. For that matter, if we are checking for overlap with individual rice patties instead of the boundaries of the field overall, then that also seems crazy. I'm pretty sure that must be what's happening because it's the only way that these numbers make sense. So I think that when it comes to homestead fitting, what we could probably do is draw a boundary around what has already been rendered, which is to say the things that we must not overlap with, and then make sure that we don't overlap with that one single shape, which seems very algorithmically simple. compared to checking whether we are overlapping with hundreds or thousands of individual tiny shapes. I would guess that this general technique would yield enormous efficiencies in both our placement algorithm generally and our unit tests specifically.

(The session measured: the fit tests the field ENVELOPE (one polygon, 49-73 vertices) and, on the polder, a 2,880-vertex dike band; the crop plots are bbox-gated and cheap; the scatter's cost is its sample count against small outlines.)

## 2026-08-28, the ruling

> Yes. I am happy with the maps being allowed to move. I do not require any of these maps to maintain bite identity now or at any time. The whole point of doing this as a scripted process is that they might change. They might even change in significant ways, and that is all fine. We are going for efficiency and historical realism and readability, but none of what we have done so far is in any way canonical. And so we need never worry at any time about maintaining any specific Map playout. on any one specific map. And, yes, I do understand that our automated checks need to fundamentally be testing the same kind of thing as our placement algorithm. Though with that being said. it might be worth thinking about the role of our automated checks in all of this. If our placement algorithm guarantees that a thing is correct, then I do not believe that there is value in running an automated check afterwards to ensure that that exact same thing is correct. The automated checks were originally developed in order to deal with the fact that we were placing items by hand, and therefore, things like overlaps could occur. But if our placement algorithm makes overlaps impossible, then checking for overlaps later in an automated check wastes time with no benefit. This makes me wonder which of our automated checks are still actually needed. Therefore, I would like for us to have not only one task for this, but I would like a follow-up task, or maybe even this will be a whole feature now that I think about it. an entire feature just for doing this kind of audit and taking a hard look at which of our automated checks are actually providing value. Now in cases where, for example, we place a label and then later on things are added to the map, then an automated check to see whether the label's placement is still valid is an example of a useful automated check. But, really, I think that what we're running up against is the fact that there is no point in an automated check, which is attempting to validate something which could never be wrong in the first place because the placement algorithm, if correct, could not have put us into an error state. This also means that many of the maps which we have saved can probably be thrown out. I mean, I'm not referring to our reference maps or any of our maps in our actual pool that we are linking to from our index. I am referring to the maps that we have saved as part of our unit tests because we do have a doctorate that any bad map becomes a test case. However, what I'm wondering now is whether our scripted process would be best served by a different approach rather than having an automated check for every map which did something wrong. If the thing which fixes the wrongness of the map is an update to our placement algorithm, then I don't think that saving off that past map actually has value. because we might not even need an automated check in order to fix what was wrong if the fix was in the placement algorithm. Therefore, we can have one hundred percent unit test coverage and have a unit test which asserts that things are now correct without saving off the old map. So I think that it is probably time to take a hard look at that and maybe even to throw out some or all of our past maps, which we have saved. Because almost all of them were saved prior to our new scripted approach, then I'm just not sure that that entire category of tests are valid anymore. So it might make sense to just throw all of it away. and then start fresh. Not for all of our unit tests away, of course, but throwing away all of the past maps which we have saved, which was saved specifically for the purpose of writing a unit test for an automated check against that map. That seems like a good next feature. But first, I would like to make the tests more efficient in the way that we are talking by measuring against a small number of line segments instead of thousands or even only dozens of vertices. So do the vertices improvement as a task and then open a new feature for this? Also, tell me what you think about this feature when the time comes because I do value your feedback on whether what I am saying makes sense. Thanks.
