### T293 (the GM asked on 2026-11-26 whether the tooling shows where a task's time is going while it is in progress, his words in `request.md` under "2026-11-26: a live view of the tasks in flight (451 T293)"; it did not: `make task-time` books a task's categories when it lands)

- **Approach**: a new read-only command, `make task-progress [BACK=<N>h] [AT=<ISO UTC>]`, which runs `l7r-gate measure task-progress`. The code is `rust/gate/crates/measure/src/measure/task_time/progress.rs` (the view), `progress/scene.rs` (who is running) and `progress/render.rs` (the text), with the audit entry `dev/audits/task-progress.md`. It prints one block for each held pool tree's builders, one for each landing in flight, a line for each page session and each review agent of the session's own, the pool's free trees, and the tasks carried into the clone that no landing has placed. No booking rule changed and `make task-time`'s output is untouched: three one-line visibility edits (`pub mod progress;`, and `pub(super)` on `book::actor` and `tiers::dir_name`) are all the existing code gives up.
  - **T293-D1, a submodule of `task_time` with its own subcommand** (CONVENTION: where code lives, no claim states it). A child module reads `task_time`'s private `sums`, `load`, `all_logs`, `bases` and `iso_of`, so nothing is copied and nothing is made public beyond the two `pub(super)`.
  - **T293-D2, a builder's minutes are the landed report's booking over its family alone** (CONVENTION). `book::book` runs over a world holding only the builder's own lines, the agents it dispatched and theirs, and their runs, and the result is summed over every key by category.   - **T293-D3, one block for each HELD POOL TREE, then one for any running builder no tree is held for** (CONVENTION). A tree's builders are found by its task, its feature number and a start at or after the tree's take, read from the registry `builder-pool.json`. Reason: a builder waiting on its plan review has STOPPED, so a rule of "a start and no stop" would drop exactly the builders a reader most wants to see; builders made 41 background Agent dispatches that day, each returning in under 2 s (observed 2026-11-26, method: the build half's count over the 451 event log's builder Agent calls).

Reason: a start with no stop is also an agent cut off; three agents had a start and no stop, two running builders and a `spec-fidelity` cut off four minutes after it started, and the latest `Stop` named exactly the two (observed 2026-11-26, method: a Python pass at 20:27Z over the 451 log's start, stop and `Stop` lines since 08:00Z).   - **T293-D5, the step now is the open make run with its LAST FINISHED phase: a DEVIATION from the task line**, which asks for "the open make span". No `Phase` line is ever open: the writer takes a span as `<step>:<t0>:<t1>:<code>` (`event_log/phase.rs`) and has no start form, so each line is written when its step ends. The phase running at this moment sits in the run's own category until its line lands, and the output's header says so. Reason for not adding a start marker: it changes the event log's writer and every reader of it, a task of its own, and the open run with its last finished phase already names where a builder is.
  - **T293-D6, a call open now is closed at the moment of the view by a line made in memory, never written** (CONVENTION).   - **T293-D7, the model turn open now is a row of its own**, `builders: the turn open now (its tool not yet known)` (CONVENTION). Reason: the booking names a turn by the call that ends it, which has not happened yet.

  - **T293-D9, a pool tree's `Phase` lines are re-tasked from the pool's log** (CONVENTION, around the open T332).
